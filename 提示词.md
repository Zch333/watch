# 一、先重新定义“达到目标”的含义

Move25 真正的最终需求不是“有一个 25/5 倒计时页面”，而是：

```text
用户设置工作节律
        │
        ▼
工作时间内可靠生成提醒计划
        │
        ▼
25 分钟工作结束
        │
        ▼
腕上提醒
        │
        ├── 起身走动
        ├── 身体伸展
        └── 远眺放松眼睛
        │
        ▼
活动 5 分钟
        │
        ▼
下一工作周期
```

默认：

```text
周一～周五
09:00–12:00
13:30–18:00
25 / 5
```

真正的产品级验收标准应是：

```text
[ ] 不打开 Move25 也能提醒
[ ] 返回表盘后能提醒
[ ] 息屏后能提醒
[ ] 应用进程不存活仍能提醒
[ ] 手机断连时明确知道是否还能提醒
[ ] 重启后设置和状态正确恢复
[ ] 时区变化不产生累计漂移
[ ] 暂停/跳过/关闭不会留下孤儿提醒
[ ] 所有降级均明确展示
[ ] 不依赖后台 JS 长计时器
```

因此当前项目距离目标最大的差距已经不是 Domain，而是**可靠 Reminder Delivery**。

# 二、当前架构总体评价

现在这套 FUNAR / Functional DDD / Hexagonal Architecture 已经基本形成正确骨架：

```text
HML / Page
    │
    ▼
MVU
    │
    ▼
Application Shell
    │
    ▼
decide / evolve
    │
    ▼
Domain
    │
Ports
    │
    ├── Clock
    ├── Calendar
    ├── Store
    ├── Reminder
    ├── Haptics
    ├── Diagnostics
    └── Navigation
         ▲
         │
Adapters
```

`domain/` 没有平台 API，系统存储、振动、路由和提醒都已经放入适配器；`StorePort/v2` 也已经明确把 native callback 作为 durability boundary。

尤其是这次 Storage 重构是正确方向：当前 `system-store.js` 已经不再在 `storage.set()` 请求刚发出时就推进 revision，而是在 native `success` 回调后才更新 committed snapshot；失败或超时保留旧 revision。

所以：

> **不要重写 Domain。现在需要重构的是 Imperative Shell、UI command completion、Effect ordering 和 delivery architecture。**

# 四、P0-2：Store 已异步化，但大部分 UI 仍按“同步 dispatch”工作

这是当前代码最重要的新一致性问题。

设置页已经正确升级：

```js
app.dispatch(message, function (nextModel, result) {
    // 只有 native storage commit 成功之后才离开页面。
});
```

这是正确的。

但首页仍然：

```js
model = app.dispatch({
    tag: 'StartNowPressed'
});

// dispatch 可能仍在等待 storage callback，
// 这里却已经开始导航。
app.navigateTo('break-active');
```

更多页同样：

```js
var model = app.dispatch(message);

if ((model.errors || []).length === 0) {
    app.navigateTo('home');
}
```

活动页也一样：

```js
var next = app.dispatch({
    tag: 'CompletePressed'
});

app.navigateTo('home');
```

以及：

```js
app.dispatch({
    tag: 'BreakElapsed'
});

app.navigateTo('home');
```

但是 `StorePort/v2` 明确规定：

> callback 收到 `Ok` 之前，snapshot **不是 durable**。

所以现在可能出现：

```text
用户点击“立即活动”
        ↓
Domain candidate = Active
        ↓
storage.set 尚未成功
        ↓
UI 已经进入 break-active
        ↓
storage.set FAIL
        ↓
Domain committed state 仍然是 NoBreak
        ↓
页面和持久化状态不一致
```

这是当前 **最高优先级业务一致性 Bug**。

# 五、前端应该全面切换为“Command Completion 驱动”

所有改变领域状态的页面操作必须遵循：

```text
点击
 ↓
dispatch(command)
 ↓
Pending
 ↓
native persistence
 ↓
Ok
 ↓
导航 / UI success
```

而不是：

```text
点击
 ↓
dispatch()
 ↓
立刻导航
```

## 首页建议修改

```js
export default {
    data: {
        commandBusy: false,
        hasError: false,
        errorText: ''
    },

    onStartNow() {
        // 防止用户连续点击产生重复 command。
        if (this.commandBusy) {
            return;
        }

        var app = runtime();

        if (!app ||
            typeof app.isReady !== 'function' ||
            !app.isReady()) {

            this.hasError = true;
            this.errorText = '应用仍在初始化，请稍候';
            return;
        }

        this.commandBusy = true;
        this.hasError = false;

        var page = this;

        app.dispatch(
            {
                tag: 'StartNowPressed'
            },

            function (model, result) {
                // callback 才是真正的 command completion。
                page.commandBusy = false;

                if (!result ||
                    result.tag !== 'Ok') {

                    var errors =
                        model && model.errors
                            ? model.errors
                            : [];

                    page.hasError = true;

                    page.errorText =
                        errors.length > 0
                            ? (
                                errors[
                                    errors.length - 1
                                ].text ||
                                errors[
                                    errors.length - 1
                                ].code ||
                                '无法开始活动'
                            )
                            : '无法开始活动';

                    return;
                }

                /*
                 * 只有 committed state 已经成功以后
                 * 才允许切换页面。
                 */
                var navigation =
                    app.navigateTo(
                        'break-active'
                    );

                if (navigation &&
                    navigation.tag === 'Err') {

                    page.hasError = true;
                    page.errorText =
                        '活动已开始，但页面打开失败';
                }
            }
        );
    }
};
```

# 六、`onToggle()` 也必须等待 commit

当前：

```js
app.dispatch(message);
this.syncModel();
```

异步 Store 下会导致：

```text
点击启用
→ UI 立即 refresh
→ committed state 尚未改变
→ 页面仍显示“已关闭”
→ 几百毫秒后实际提交成功
→ 用户误以为点击无效
→ 再点一次
```

改成：

```js
onToggle() {
    if (this.commandBusy) {
        return;
    }

    var app = runtime();

    if (!app || !app.isReady()) {
        this.syncModel();
        return;
    }

    var current = app.refresh();

    if (!current.canSchedule) {
        this.syncModel();
        return;
    }

    var message =
        current.planStatus === 'Enabled' ||
        current.planStatus === 'Paused'
            ? { tag: 'DisablePressed' }
            : { tag: 'EnablePressed' };

    this.commandBusy = true;

    var page = this;

    app.dispatch(
        message,

        function (_model, result) {
            page.commandBusy = false;

            if (!result ||
                result.tag !== 'Ok') {

                page.hasError = true;
                page.errorText =
                    '计划状态修改失败';

                page.syncModel();
                return;
            }

            /*
             * committed state 已改变，
             * 此时刷新才有明确语义。
             */
            page.syncModel();
        }
    );
}
```

# 八、P0-3：Domain 和 Page 同时负责 Navigation

当前属于明显的“双 owner”。

例如 `StartBreakNow` 最终会生成：

```js
[
    vibrate('BreakStart'),
    navigate('break-active')
]
```

与此同时首页又：

```js
app.navigateTo('break-active');
```

所以 Router Adapter 不得不专门加入：

```js
if (
    route === lastRoute &&
    now - lastNavigationAt < 100
) {
    return ok(...);
}
```

来消除 100ms 内重复导航。

这其实是在 Adapter 中补偿上层架构问题。

## 建议

**Navigation 不属于 Domain。**

Domain 应该表达：

```text
BreakStarted
BreakFinished
BreakSkipped
```

不应该表达：

```text
pages/break-active
pages/home
```

因此应该从：

```text
domain/effects.js
```

逐步删除：

```js
navigate(...)
```

`Navigate` 归 MVU/Application UI shell。

领域改为：

```js
case 'CompleteBreak': {
    // ...

    return decideSnapshot(
        state,

        [
            breakFinished(
                state.breakSession.sessionId,
                nowResult.value,
                completedOutcome()
            )
        ],

        [
            // Domain 只表达用户语义反馈。
            vibrate('BreakEnd')

            // 不再 navigate('home')
        ]
    );
}
```

`StartBreakNow`：

```js
const effects = acknowledged
    ? []
    : [
        // 用户主动开始活动时给一次触感反馈。
        vibrate('BreakStart')
    ];

return decideSnapshot(
    state,

    [
        breakStarted(
            sessionId,
            now,
            endsAtResult.value,
            selected.guidance.id,
            selected.nextIndex
        )
    ],

    effects
);
```

页面 callback 成功后再导航。

完成之后 Router Adapter 中这段：

```js
lastRoute
lastNavigationAt
100ms duplicate window
```

可以删除。

这是更深层的 FUNAR 问题。

当前 `command-handler` 顺序是：

```text
decide
 ↓
interpretEffect
 ↓
settle
 ↓
evolve
 ↓
saveSnapshot
```

因此：

```text
Vibrate
Navigate
Reminder Register
Reminder Cancel
Diagnostics
```

都混在同一个 Effect 队列里。

这会造成：

```text
vibrate 成功
```

# 十、FUNAR 下应该增加 Effect Phase

我建议在 Application 层定义：

```text
RequiredBeforeCommit
BestEffortAfterCommit
Telemetry
```

而不是让 Domain 知道数据库事务。

例如：

```js
function classifyEffect(effect) {
    switch (effect.tag) {

        /*
         * 这些外部资源必须先成功，
         * Domain 才能宣称计划 Enabled/Disabled。
         */
        case 'RegisterReminders':
        case 'CancelReminders':
            return 'RequiredBeforeCommit';

        /*
         * 这些属于用户反馈。
         * 不应该发生在持久化成功之前。
         */
        case 'Vibrate':
            return 'BestEffortAfterCommit';

        /*
         * 日志不能影响业务事务。
         */
        case 'EmitDiagnostic':
            return 'Telemetry';

        default:
            return 'Unknown';
    }
}
```

Command Handler 目标顺序：

```text
Facts
 ↓
decide
 ↓
RequiredBeforeCommit
 ↓
settle
 ↓
evolve
 ↓
Persist
 ↓
BestEffortAfterCommit
 ↓
返回 Ok
```

即：

```js
function splitEffects(effects) {
    var required = [];
    var afterCommit = [];
    var telemetry = [];

    for (
        var index = 0;
        index < effects.length;
        index += 1
    ) {
        var effect = effects[index];
        var phase =
            classifyEffect(effect);

        if (
            phase ===
            'RequiredBeforeCommit'
        ) {
            required.push(effect);
        } else if (
            phase ===
            'BestEffortAfterCommit'
        ) {
            afterCommit.push(effect);
        } else {
            telemetry.push(effect);
        }
    }

    return {
        required: required,
        afterCommit: afterCommit,
        telemetry: telemetry
    };
}
```

这会让你的：

> Functional Core / Imperative Shell

真正形成可靠的 commit protocol，而不仅仅是代码目录结构。

# 十一、P0-5：`refresh()` 的 temporal persistence 和 command persistence 现在有竞争条件

当前 shell 有两个独立锁：

```js
pendingCommand
pendingTemporalPersist
```

但是 `dispatch()` 只阻止：

```js
if (pendingCommand) {
    ...
}
```

却没有阻止：

```text
pendingTemporalPersist === true
```

这会产生这样的竞争：

```text
活动倒计时到 00:00
        ↓
refresh()
        ↓
reduceTemporalState()
        ↓
saveSnapshotAsync()
        ↓
pendingTemporalPersist = true
        ↓
state 仍然是 Active
        ↓
页面看到
Active + remaining = 0
        ↓
发送 BreakElapsed
        ↓
dispatch()
        ↓
再次尝试写同 revision
        ↓
PERSISTENCE_PENDING
```

而当前活动页确实会在时间到 0 后立即：

```js
app.dispatch({
    tag: 'BreakElapsed'
});
```

## 建议

不要让 `BreakElapsed` 再承担状态归约。

你已经有：

```js
reduceTemporalState()
```

所以：

> **时间自然流逝只由 `refresh()` 归约；页面 timer 只负责重新读取。**

活动页改为：

```js
var tick = function () {
    var app = runtime();

    if (!app || !app.isReady()) {
        self.timerId =
            scheduleVisibleTimer(
                tick,
                250
            );
        return;
    }

    var model = app.refresh();

    self.remainingText =
        formatSeconds(
            model.remainingSeconds
        );

    /*
     * 仍是 Active：
     * 只继续刷新。
     *
     * 即使时间已经到 0，
     * 也不要再 dispatch BreakElapsed；
     * refresh() 已经负责 temporal reduction。
     */
    if (
        model.breakStatus ===
        'Active'
    ) {
        self.timerId =
            scheduleVisibleTimer(
                tick,
                model.remainingSeconds > 0
                    ? 1000
                    : 250
            );

        return;
    }

    if (
        model.breakStatus ===
        'Finished'
    ) {
        self.stopVisibleTicker();

        /*
         * 可以留在结束页面，
         * 或由 UI 决定返回首页。
         */
        self.finished = true;
        self.showFinished = true;
    }
};
```

然后逐步删除：

```text
BreakElapsed
```

这个 UI command。

# 十六、P1：Storage 不可用时，不应该让整个 Move25 完全瘫痪


```js

  | Ephemeral

```

```kotlin
interface ReminderScheduler {
```

```kotlin
    val dueAtEpochMs: Long,

)
```

# 二十七、Android AlarmManager Adapter

Android 当前对 exact alarm 有严格限制。Android 14 对很多新安装应用默认不会预授予 `SCHEDULE_EXACT_ALARM`；调用精确 API 前需要通过 `canScheduleExactAlarms()` 检查，并在无权限时显式降级。([Android Developers][5])

因此：

```kotlin
class AlarmManagerReminderScheduler(
    private val context: Context
) : ReminderScheduler {

    private val alarmManager =
        context.getSystemService(
            AlarmManager::class.java
        )

    override fun schedule(
        reminder: ScheduledReminder
    ): ScheduleResult {

        val intent =
            Intent(
                context,
                BreakAlarmReceiver::class.java
            ).apply {

                // 只传领域稳定身份。
                putExtra(
                    "semanticKey",
                    reminder.semanticKey
                )

                putExtra(
                    "breakMinutes",
                    reminder.breakMinutes
                )
            }

        val operation =
            PendingIntent.getBroadcast(
                context,

                /*
                 * Android ID 只是 Adapter
                 * 内部实现细节。
                 */
                reminder.semanticKey.hashCode(),

                intent,

                PendingIntent.FLAG_UPDATE_CURRENT or
                    PendingIntent.FLAG_IMMUTABLE
            )

        if (
            Build.VERSION.SDK_INT >=
                Build.VERSION_CODES.S &&
            !alarmManager
                .canScheduleExactAlarms()
        ) {

            /*
             * 无精确闹钟权限：
             * 明确进入 degraded。
             */
            alarmManager.setAndAllowWhileIdle(
                AlarmManager.RTC_WAKEUP,
                reminder.dueAtEpochMs,
                operation
            )

            return ScheduleResult.Degraded
        }

        alarmManager
            .setExactAndAllowWhileIdle(
                AlarmManager.RTC_WAKEUP,
                reminder.dueAtEpochMs,
                operation
            )

        return ScheduleResult.Scheduled
    }
}
```

Google 官方也明确提醒 exact alarms 会增加系统资源和电池消耗，因此不要简单把所有周期性后台工作都升级为 exact alarm。([Android Developers][6])

对于 Move25 可以设计成：

```text
Exact permission available
→ 精确模式

无权限
→ 近似提醒
→ UI 显示“可能有少量延迟”
```

```kotlin
class BreakAlarmReceiver :
    BroadcastReceiver() {

    override fun onReceive(
        context: Context,
        intent: Intent
    ) {
        val key =
            intent.getStringExtra(
                "semanticKey"
            ) ?: return

        val notification =
            BreakNotification(
                semanticKey = key,

                body =
                    "走动、伸展一下，并看看远处"

        /*

         *
         * 它只调用业务语义 Port。

        AppGraph
            .wearNotificationPort
            .sendBreakReminder(

                    .record(
                        key,
                        result
                    )
            }
    }
}
```
