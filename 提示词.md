

# 当前判断：不要继续堆领域功能，接下来要攻克“真实设备闭环”

我重新按当前 `Zch333/watch` 默认分支做了一轮审阅。项目和前几轮相比已经发生了实质变化：现在已经有 Lite Wearable 设备适配器、独立 device composition root、真实时钟/时区、`@system.storage`、`@system.vibrator`、能力缺口适配器、MVU 页面，以及用于绕过 Lite FA loader 黑屏问题的自定义 Hvigor 构建桥。README 当前声明有 **198 个宿主测试通过**，但模拟器交互、存储/振动真机验证、签名和 GT6 真机能力探针仍未完成。

同时，当前安装的 API 24 Lite Wearable SysCap 被项目核查为**没有 ReminderAgent**，设备适配器因此明确返回 `Unsupported`，而不是伪造系统后台提醒。

这意味着项目现在最大的矛盾已经不是 FUNAR/DDD 写得够不够好，而是：

> **现有 GT6 Lite Wearable 公开能力尚不能兑现“应用退出/息屏后每 25 分钟可靠提醒”这个核心产品承诺。**

所以接下来的优化顺序必须改变。

# 一、重新明确最终需求

最终产品至少需要满足四个等级。

## P0：必须实现

核心节律：

```text
工作 25 分钟
        ↓
腕上提醒
        ↓
活动 5 分钟
├─ 起身走动
├─ 伸展肩颈/腰髋/手腕
└─ 看向远处放松眼睛
        ↓
下一轮
```

默认：

```text
周一～周五
09:00–12:00
13:30–18:00
25 / 5
```

并且必须支持：

* 启用/关闭；
* 暂停 1 小时；
* 暂停今天；
* 跳过下一次；
* 立即活动；
* 工作日设置；
* 工作时段设置；
* 工作/活动时长设置；
* 应用重启恢复；
* 时区变化恢复；
* 设置本地持久化；
* 能力失败明确显示。

真正重要的验收标准是：

> 用户不打开 Move25、手表息屏、应用进程不存活时，到时间仍然能获得提醒。

如果做不到这一条，则“番茄钟页面做得再漂亮”也没有达到原始需求。

# 二、当前建议的产品架构需要从 Standalone-only 升级为 Standalone-first

当前项目将：

```text
ReminderCapability = Unsupported
```

处理得很诚实。`createUnsupportedReminder()` 不会注册虚假提醒。

但如果一直坚持：

```text
只能纯 GT6
且
必须后台提醒
```

那么在当前公开 SDK 条件下，项目会卡死。

更合理的最终架构应是：

```text
                 Reminder Delivery
                       │
        ┌──────────────┼──────────────┐
        │              │              │
 WatchStandalone    PhoneRelay     ManualOnly
        │              │              │
 GT6 系统提醒      手机可靠调度       手动活动
 未来若开放       ↓
                Wear Engine
                   ↓
                 GT6
```

即：

```text
优先级 1：WatchStandalone
        GT6 自己定时
        ↓ 不可用
优先级 2：PhoneRelay
        手机系统定时
        ↓
        腕上提醒
        ↓ 不可用
优先级 3：ManualOnly
        只允许“立即活动”
```

这不破坏六边形架构，反而是它真正发挥作用的场景。

华为当前 Wear Engine 官方页面明确提供手机—穿戴通信以及由手机应用向穿戴设备发送通知的能力；中文页面目前列出了 Android 和 iOS 两个平台。([华为开发者][1]) 2026 年 5 月更新的官方 iOS Wear Engine 文档也确实提供手机与穿戴应用之间的 P2P 通信，因此 iPhone 后续并非理论上的死路。([华为开发者][2])

但英文 Wear Engine 产品首页目前只列 Android，因此平台资料仍存在不一致。第一手机端应该明确选择 **Android/vivo X200**，iOS 单独验证，不要一次同时写三端。([华为开发者][3])

# 四、目前最严重的架构漏洞：StorePort 的契约与实际实现不一致

这个问题比 UI 更严重。

`StorePort` 明确要求：

```text
saveSnapshot(expectedRevision, snapshot)
→ Result<StoreError, Revision>
```

而且契约明确写着：

> saveSnapshot 必须是 all-or-nothing；失败后之前的有效快照仍应可读取。

但真实 `system-store.js` 当前调用：

```js
storage.set({
    key: SNAPSHOT_KEY,
    value: encoded,

    success: function () {
        persistenceState = 'Ready';
    },

    fail: function (...) {
        persistenceState = 'Failed';
    }
});

// 系统回调还没有返回
stored = snapshot;
revision = snapshot.revision;

// 已经告诉上层“成功”
return ok(...);
```

这意味着：

```text
storage.set 请求提交
        ↓
Move25 返回 Ok
        ↓
Domain/Application 认为已经持久化
        ↓
随后系统回调 fail
        ↓
实际上没有持久化
```

而 `command-handler.js` 的注释和实现语义是：

> 只有 settled state 已经 durable persisted，才返回 Ok。

两者现在是矛盾的。

这是典型的 **Port Contract Violation**。

# 五、后端第一项重构：把 IO 异步性显式放到 Imperative Shell

这里的“后端”不是传统服务器，而是：

```text
Domain
Application
Ports
Adapters
Effect Interpreter
```

不要为了保持同步接口而欺骗领域。

## StorePort v2

建议改成 callback，因为 Lite JS 环境比 Promise 更值得保守处理：

```js
/**
 * StorePort/v2
 *
 * 注意：
 * callback 返回之前，绝不能认为数据已经持久化。
 */
export function createStorePortContract() {
    return {
        loadSnapshot: function (done) {
            // done(Result<StoreError, Option<Snapshot>>)
        },

        saveSnapshot: function (
            expectedRevision,
            snapshot,
            done
        ) {
            // done(Result<StoreError, Revision>)
        },

        readStatus: function () {
            // 同步读取 adapter 当前状态即可。
        }
    };
}
```

真实 Adapter：

```js
export function createLoadedStore(initial) {
    var stored = initial;
    var revision =
        initial &&
        typeof initial.revision === 'number'
            ? initial.revision
            : 0;

    return {
        saveSnapshot: function (
            expectedRevision,
            snapshot,
            done
        ) {
            // 乐观并发检查仍然发生在 Port 边界。
            if (expectedRevision !== revision) {
                done(err(storeError(
                    STORE_ERROR_CODES.CONCURRENT_MODIFICATION,
                    {
                        expected: expectedRevision,
                        current: revision
                    }
                )));
                return;
            }

            var encoded;

            try {
                encoded = JSON.stringify(snapshot);
            } catch (error) {
                done(err(storeError(
                    STORE_ERROR_CODES.IO_FAILURE,
                    String(error)
                )));
                return;
            }

            storage.set({
                key: SNAPSHOT_KEY,
                value: encoded,

                success: function () {
                    /*
                     * 关键：
                     * 只有 native storage 真正报告成功后，
                     * 才更新内存中的 committed snapshot。
                     */
                    stored = snapshot;
                    revision = snapshot.revision;

                    done(ok(Object.freeze({
                        tag: 'Revision',
                        value: revision
                    })));
                },

                fail: function (message, code) {
                    /*
                     * 失败时绝不能修改 stored/revision。
                     * 因此旧的有效快照仍然成立。
                     */
                    done(err(storeError(
                        STORE_ERROR_CODES.IO_FAILURE,
                        {
                            message: message,
                            code: code
                        }
                    )));
                }
            });
        }
    };
}
```

这样才能真正满足现有端口契约。

# 六、Command Handler 也应该演进成异步 Effect Shell

不要把 `async` 污染到 domain。

Domain 仍然保持：

```text
decide(state, command, facts)
→ Decision(events, effects)
```

纯函数不变。

改变的是 Application Shell：

```text
Facts
 ↓
decide()
 ↓
执行 Effects
 ↓
Effect Results
 ↓
settle()
 ↓
evolve()
 ↓
saveSnapshot()
 ↓
成功以后才 commit
```

建议接口：

```js
export function createCommandExecutor(ports) {

    return function execute(
        committedState,
        command,
        onComplete
    ) {
        /*
         * 1. 收集 Facts。
         * 这里可以读取 clock/calendar。
         */

        var factsResult = collectFacts(
            ports,
            committedState,
            command
        );

        if (factsResult.tag === 'Err') {
            onComplete(factsResult);
            return;
        }

        /*
         * 2. Domain 纯决策。
         */
        var decisionResult = decide(
            committedState,
            command,
            factsResult.value
        );

        if (decisionResult.tag === 'Err') {
            onComplete(decisionResult);
            return;
        }

        /*
         * 3. 执行外部效果。
         * 未来 Reminder 可以是 Watch、
         * Android Relay 或其他 Adapter。
         */
        executeEffects(
            decisionResult.value.effects,
            ports,
            function (effectResults) {

                /*
                 * 4. 用 EffectResult settlement
                 * 决定 Plan 到底有没有真的 Enabled。
                 */
                var settled = settlePlanLifecycle(
                    committedState,
                    decisionResult.value.events,
                    effectResults.registration
                );

                if (settled.tag === 'Err') {
                    onComplete(settled);
                    return;
                }

                /*
                 * 5. Domain evolve 仍然纯。
                 */
                var evolved = evolveAll(
                    committedState,
                    settled.value
                );

                if (evolved.tag === 'Err') {
                    onComplete(evolved);
                    return;
                }

                var candidate = evolved.value;

                /*
                 * 6. 最终状态真正写盘。
                 */
                ports.store.saveSnapshot(
                    committedState.revision,
                    createSnapshot(candidate),
                    function (saved) {

                        if (saved.tag === 'Err') {
                            /*
                             * 外界操作可能已经执行，
                             * 但 committedState 仍保持旧状态。
                             * 后续 Reconcile 负责收敛。
                             */
                            onComplete({
                                tag: 'Err',
                                error: saved.error,
                                state: committedState,
                                candidateState: candidate
                            });
                            return;
                        }

                        /*
                         * 到这里才允许 UI 把 candidate
                         * 当作 committed state。
                         */
                        onComplete({
                            tag: 'Ok',
                            state: candidate
                        });
                    }
                );
            }
        );
    };
}
```

这才真正符合：

> Functional Core + Imperative Shell。

# 七、`openSystemStore()` 的 500ms fallback 需要重新设计

现在逻辑是：

```text
storage.get()
   │
   ├─ 500ms 内成功 → persistent store
   │
   └─ 超过500ms → memory fallback
```

而一旦 fallback 调用了 `finish()`，稍后真实 storage callback 会因为 `completed === true` 被丢弃。

这可能造成：

```text
磁盘其实有原来的用户设置
        ↓
仿真器/设备 IO 只是慢
        ↓
500ms timeout
        ↓
应用启动成默认值
        ↓
用户保存
        ↓
运行过程中实际上处于另一套状态
```

产品构建不应该做这种无声 fallback。

建议：

```js
export function openSystemStore(
    options,
    onReady
) {
    var timeoutMs =
        options && options.timeoutMs
            ? options.timeoutMs
            : 3000;

    var finished = false;

    storage.get({
        key: SNAPSHOT_KEY,

        success: function (value) {
            if (finished) {
                return;
            }

            finished = true;

            onReady({
                tag: 'Persistent',
                store: createLoadedStore(
                    decode(value)
                )
            });
        },

        fail: function (message, code) {
            if (finished) {
                return;
            }

            finished = true;

            /*
             * 明确报告不可用，
             * 不伪装成持久化成功。
             */
            onReady({
                tag: 'Unavailable',
                error: {
                    code: code,
                    message: message
                }
            });
        }
    });

    setTimeout(function () {
        if (finished) {
            return;
        }

        finished = true;

        onReady({
            tag: 'Unavailable',
            error: {
                code: 'STORAGE_TIMEOUT',
                message:
                    'Persistent storage did not respond'
            }
        });
    }, timeoutMs);
}
```

然后 UI 显示：

```text
本地存储暂不可用
本次设置可能不会保存
```

而不是假装一切正常。


```js
    return Object.freeze({
        tag: 'Supported',
```

# 十一、Android 调度 Adapter 的建议实现

Android 当前对精确定时有明确限制。对于 Android 12+，精确闹钟通常需要 `SCHEDULE_EXACT_ALARM` 特殊访问；Android 14 对新安装应用默认不会自动授予该能力，应先调用 `canScheduleExactAlarms()`。Google 也要求只有真正的用户可见精确定时场景才使用 exact alarms。([Android Developers][4])

Move25 的 25 分钟到点提醒属于用户主动配置的时间敏感功能，因此可以设计“精确提醒可选能力”，但需要提供无权限时的降级。([Android Developers][4])

例如 Kotlin：

```kotlin
class AndroidReminderScheduler(
    private val context: Context
) {

    private val alarmManager =
        context.getSystemService(
            AlarmManager::class.java
        )

    fun schedule(
        reminder: ReminderDto
    ): ScheduleResult {

        /*
         * Android 12+：
         * 精确闹钟必须先检查系统能力。
         */
        if (
            Build.VERSION.SDK_INT >=
                Build.VERSION_CODES.S &&
            !alarmManager.canScheduleExactAlarms()
        ) {
            return ScheduleResult.PermissionRequired
        }

        val intent =
            Intent(
                context,
                BreakReminderReceiver::class.java
            ).apply {

                /*
                 * semanticKey 是跨系统稳定身份。
                 * 不把 Android requestCode
                 * 当领域身份。
                 */
                putExtra(
                    "semanticKey",
                    reminder.semanticKey
                )

                putExtra(
                    "breakMinutes",
                    reminder.breakMinutes
                )
            }

        val pendingIntent =
            PendingIntent.getBroadcast(
                context,

                /*
                 * 对 key 做稳定 hash。
                 */
                reminder.semanticKey.hashCode(),

                intent,

                PendingIntent.FLAG_UPDATE_CURRENT or
                    PendingIntent.FLAG_IMMUTABLE
            )

        alarmManager.setExactAndAllowWhileIdle(
            AlarmManager.RTC_WAKEUP,
            reminder.dueAtEpochMs,
            pendingIntent
        )

        return ScheduleResult.Scheduled
    }
}
```

如果没有 exact alarm 权限，则明确降级为：

```kotlin
alarmManager.setAndAllowWhileIdle(
    AlarmManager.RTC_WAKEUP,
    reminder.dueAtEpochMs,
    pendingIntent
)
```

但 UI 必须显示：

```text
提醒时间可能有延迟
```

而不是仍然标为“精确”。

# 十二、Android Alarm 到点以后不要直接污染业务层

Receiver：

```kotlin
class BreakReminderReceiver :
    BroadcastReceiver() {

    override fun onReceive(
        context: Context,
        intent: Intent
    ) {
        val key =
            intent.getStringExtra(
                "semanticKey"
            ) ?: return

        /*
         * Infrastructure 层调用 Gateway。
         * Receiver 不包含业务规则。
         */
        val gateway =
            AppGraph.wearNotificationGateway

        gateway.sendBreakReminder(
            BreakNotification(
                semanticKey = key,
                title = "该活动了",
                body =
                    "起身活动5分钟，伸展身体，看看远处"
            )
        )

        /*
         * 同时给手机本身发本地通知，
         * 即使手表断连也不会完全丢提醒。
         */
        AppGraph.localNotifier
            .showBreakReminder(key)
    }
}
```

华为 Wear Engine 的具体 `NotifyClient` 调用应单独放：

```text
HuaweiWearEngineNotificationAdapter
```

不要散落进 `BroadcastReceiver`。

华为官方确实提供手机端向穿戴设备发送模板化消息通知的能力，这个 Adapter 值得重点做真机 Probe。([华为开发者][1])

# 十四、不要在 HML 中依赖复杂布尔表达式

当前有：

```html
show="{{!canSchedule}}"
```

活动页还有：

```html

```

这未必一定失败，但考虑到你已经遇到过 Lite HML/CSS 编译和黑屏兼容问题，不值得把复杂表达式留在模板。

华为 Lite JS 示例的典型模式是把布尔状态放入 JS 数据字段，然后模板直接绑定。([华为开发者][5])

改成：

```js
data: {
    canSchedule: false,

    // 模板只消费简单 bool。
    showScheduleHint: true
},

syncModel: function () {
    var model = app.refresh();

    this.canSchedule =
        !!model.canSchedule;

    this.showScheduleHint =
        !this.canSchedule;
}
```

HML：

```html
<input
    type="button"
    class="btn"
    value="{{toggleText}}"
    show="{{canSchedule}}"
    onclick="onToggle">
</input>

<text
    class="hint"
    show="{{showScheduleHint}}">
    定时提醒不可用，仍可立即开始活动
</text>
```

活动页同理：

```js
this.showActiveControls =
    model.breakStatus === 'Active';

this.showFinished =
    model.breakStatus === 'Finished';
```

不要让 HML 负责推导业务状态。

# 十五、当前动作建议存在一个回归

领域中的指导动作是稳定 ID：

```text
stand_and_walk
simple_stretch
look_far
```

这是正确的。

而 `labels.js` 已经定义了中文映射：

```text
站起来走动
简单伸展
看向远处放松眼睛
```

但当前 `projectModel()` 仍直接返回：

```js
actions: item.actions
```

活动 HML 又直接：

```html
<text for="{{actions}}">
    {{$item}}
</text>
```

所以真实页面可能重新显示：

```text
stand_and_walk
simple_stretch
look_far
```

而不是中文。

正确修法不是污染 Domain，而是在 Projection 层转换：

```js
import {
    actionLabels
} from './labels.js';

function guidanceFor(
    session,
    guidanceIndex
) {
    if (!session) {
        return null;
    }

    var item =
        resolveGuidance(
            session,
            guidanceIndex
        );

    if (!item) {
        return null;
    }

    return Object.freeze({
        /*
         * id 保留领域语义身份。
         */
        id: item.id,

        /*
         * ViewModel 才负责转为展示文案。
         */
        actions: Object.freeze(
            actionLabels(item.actions)
        )
    });
}
```

这正符合：

```text
Domain → semantic ID
Projection → display text
View → render only
```

# 十七、`runtime()` 的六份复制暂时不要“为了 DRY”强行消除

目前各页面都复制了：

```js
function runtime() {
    ...
}
```

从普通 Web 工程看很丑。

但你这里有特殊背景：

> Lite 页面 loader 对相对 import 出现过实际黑屏/`require` 问题。

所以此阶段不要为了 DRY 又写：

```js
import {
    runtime
} from '../runtime.js';
```

然后重新把页面打坏。

这是一个值得**有意识接受的重复**。

可以增加一致性测试：

```js
test(
    'all Lite pages use the same runtime bridge contract',
    function () {
        // 检查页面必须访问
        // __MOVE25_LITE_RUNTIME__
        // 或 getApp fallback。
    }
);
```

等整个页面模块都由可靠 bundler 统一处理以后再消除。

这正是 KISS 优先于形式主义 DRY。

# 最关键的决策

目前代码量已经不是问题。

接下来真正决定项目成败的是四件事：

1. **让 GitHub fresh clone 和 DevEco Build/Run 100% 可复现。**
2. **修复 `StorePort` 的同步契约与异步系统 API 之间的根本矛盾。**
3. **完成 GT6 Storage/Vibrator/Loader 的真机证据链。**
4. **接受当前 GT6 Lite 后台提醒缺口，开始 Android PhoneRelay，而不是继续在纯手表端虚构 ReminderAgent。**

一旦做到第 4 点，现有 FUNAR/Functional DDD/Hexagonal Architecture 的价值会真正体现出来：

```text
Domain 完全不改
        │
ReminderSchedulerPort
        │
 ┌──────┼─────────┐
 │      │         │
GT6   Android    Future iOS
```

华为 Wear Engine 本身就是为手机—穿戴设备通信和腕上通知设计的，因此 PhoneRelay 不是“失败后的临时补丁”，而是当前公开平台能力下非常合理的正式 Adapter。([华为开发者][1])

如果仍把“纯手表独立后台定时”作为绝对不可妥协条件，那么当前工程应该进入 **Capability Blocked** 状态，而不是继续增加业务代码；只有新的 GT6 固件、Lite SDK、厂商开放能力或华为官方工单确认出现后，才重新开启 `WatchStandaloneReminderAdapter`。
