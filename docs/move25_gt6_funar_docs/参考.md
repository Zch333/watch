# 搜索结论

GitHub 上**没有发现与 `Zch333/watch` 完全同构**的项目，也就是同时满足：

* HUAWEI WATCH GT6；
* Lite Wearable / JS FA；
* 25 分钟工作＋5 分钟活动；
* 息屏、进程退出后可靠提醒；
* Standalone-first；
* FUNAR＋Functional DDD＋Hexagonal Architecture；
* 低功耗能力门禁。

但找到了几组高度相关项目。它们分别覆盖你的工程所需的不同部分：**GT6 真机工程、Lite Wearable 约束、计时与震动、手机通信、签名构建以及严谨的能力验证**。

你当前仓库仍主要是 Lite Wearable 模板和架构文档，正式领域代码、端口、适配器与测试尚未实现。

---

## 第一梯队：最值得直接研究

### 1. `yushu-sjtu/harmonyos-watch-gallery-rtos`

[打开仓库](https://github.com/yushu-sjtu/harmonyos-watch-gallery-rtos)

这是目前找到的**最可信 GT6 Lite Wearable 真机样例**。

项目明确说明：

* 已在 HUAWEI WATCH GT6 真机运行；
* HarmonyOS 6.0.0.165；
* DevEco Studio 6.0.1；
* Compatible SDK 5.0.5(17)；
* JS FA；
* HML＋CSS＋JavaScript；
* Apache-2.0 许可证。

### 对你的价值

可以重点借鉴：

* `config.json`；
* GT6 页面尺寸与圆屏布局；
* 图片与资源路径；
* 页面生命周期；
* Lite JS 实际兼容语法；
* 手势和页面切换；
* 真机可安装的最小工程配置。

### 不可直接复制的部分

它是相册应用，不涉及：

* 系统后台提醒；
* 持久化工作日程；
* 定时唤醒；
* 应用退出后提醒；
* 低功耗调度。

**建议：将它作为 GT6 平台基线参照项目。**

### 2. `1122414/WatchBuddy`

[打开仓库](https://github.com/1122414/WatchBuddy)

这是与当前仓库在**工程思维和风险处理方式上最接近**的项目。

项目目标设备是 GT6 Pro，包含：

* Lite Wearable JS 表端；
* 标准 Wearable ArkTS 实验项目与 Lite 项目明确隔离；
* 能力矩阵和真机证据；
* HAP 构建、签名和工具链检查脚本；
* Android 历史验证工程；
* 服务端和协议核心；
* GT6 联网、提醒、语音和传感器能力的显式门禁；
* 不把未经验证的设备能力写成已完成事实。

它还记录了非常有价值的实际问题：

* GT6 Pro 独立联网是高风险假设；
* 不应将手机提供的网络误认为手表独立网络；
* 签名 HAP 和 Profile 必须严格校验；
* 部分权限声明可能直接导致安装错误；
* API 兼容版本必须以真机结果为准；
* 离线降级必须明确展示，不能伪装成在线功能。

### 对你的价值

重点借鉴：

```text
scripts/check-watch-toolchain.mjs
构建脚本
签名验证
真机证据目录
能力矩阵
平台约束
协议和核心逻辑分离
失败显式降级
```

### 与你的差异

* 它主要是 AI 陪伴应用；
* 有云端和网络；
* 你的 Move25 默认无网络、无云；
* 它的部分功能仍是能力探索状态。

**建议：把它作为工具链、能力治理和证据管理参考。**

### 3. `gentslava/Home-Assistant-HarmonyOS-Next`

[打开仓库](https://github.com/gentslava/Home-Assistant-HarmonyOS-Next)

重点查看：

```text
apps/watch-lite/
docs/platform-constraints.md
```

这个仓库明确区分：

* GT4/GT5/GT6：Lite Wearable；
* 标准智能手表：ArkTS Wearable；
* FA＋`config.json`；
* HML/CSS/JS；
* JerryScript / ACE Lite；
* ES5.1 兼容约束。

README 还给出了实际约束：

* HAP 不超过约 10 MB；
* 单页面体积有限；
* 内存非常有限；
* 无普通后台执行；
* 路由没有标准回退栈；
* 重启后状态不会自动恢复；
* 图片解码后的内存远大于压缩文件；
* GT 系列不能按标准 HDC/Wi-Fi 调试流程安装。

### 对你的价值

它比普通示例更接近一个真实多页面应用，可参考：

* 页面目录组织；
* 共享状态；
* Repository 抽象；
* Mock 实现；
* 多语言；
* P2P 通信；
* Lite 和 ArkTS 两套实现保持契约一致；
* 资源预算。

### 风险

它的结构包含面向具体项目的 store 和 repository，不应原封不动迁入你的 FUNAR 架构。

**建议：借鉴运行时限制与多页面实现，不照搬状态管理。**

### 对你的价值

适合加入本地审查流程，用于检查：

* 大图；
* 超出 Lite 运行时的语法；
* 错误 HML 组件；
* 资源路径；
* 音频使用；
* 内存风险。

### 注意

这是社区维护项目，不是华为官方 SDK 事实源。它的检查结果应当作为：

```text
启发式审查
```

而不是：

```text
设备能力证明
```

## 第二梯队：功能和交互相关

### 5. `samlach2222/WatchTronome`

[打开仓库](https://github.com/samlach2222/WatchTronome)

这是 Watch GT2 Pro 上的 LiteOS 节拍器应用，通过手表振动提供节拍，并曾通过华为运动健康应用市场分发。

### 与 Move25 的相似点

* 周期性计时；
* 震动反馈；
* 极简圆屏界面；
* Lite 手表应用；
* 已有真实应用市场分发经验。

### 可以借鉴

* 振动 API 的调用方式；
* 节奏控制；
* 数值选择器；
* 圆屏按钮布局；
* 隐私政策形式；
* Lite Wearable 应用发布结构。

### 不能证明

节拍器通常在应用前台持续执行。它**不能证明**：

* 息屏后仍可靠计时；
* 应用退出后仍提醒；
* 系统级提醒代理存在；
* 低功耗 25 分钟后台调度可行。

它是交互参考，不是后台能力证据。

# 最重要的发现

目前公开 GitHub 项目中，**仍未找到一个能够证明 GT6 Lite Wearable 普通三方应用可在以下全部场景可靠定时提醒的项目**：

```text
返回表盘
息屏
应用进程退出
手机蓝牙断开
低电量模式
手表重启
```

也没有找到 Lite Wearable 项目公开使用并真机验证：

```text
reminderAgentManager
PUBLISH_AGENT_REMINDER
系统级后台 25 分钟定时唤醒
```

GitHub 代码搜索 `PUBLISH_AGENT_REMINDER + liteWearable` 的结果基本只有权限文档，没有可确认的 GT 系列应用实现。

因此，你当前仓库的核心策略仍然正确：

> **参考其他项目学习工程结构和交互，但后台提醒必须由自己的 GT6 能力探针得出结论，不能从其他标准 Wearable 或前台计时项目推断。**
